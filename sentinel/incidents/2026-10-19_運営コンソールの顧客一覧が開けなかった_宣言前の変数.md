## なぜ起きたか(コード)

```ts
const customTooShort = (["owner", "manager", "staff"] as const).some(
  (r) => roles[r] && (r !== "manager" || roleSplit) && ...,   // その場で実行され roleSplit を読む
);
const roleSplit = planFeaturesFromLimits(...).roleSplit;        // 宣言はこの下 → ReferenceError
```

- `.some(...)` のコールバックはその行で**すぐ**実行される。`roleSplit` は宣言前(TDZ)なので ReferenceError
- 店長(`manager`)の発行は初期状態でオンなので、描画のたびに**必ず**落ちた
- TypeScript は「関数の中から後で宣言する const を読む」をエラーにしない。lint の `no-use-before-define` は
  正しい書き方(イベントハンドラが後の const を読む)まで誤検出するので掛けていない。描画するテストも無かった
- 本番ではビルドで変数名が縮められ、`'P'`(サーバー側の束)・`'U'`(画面側の束)と出た。文面から原因の変数は追えない

## なぜ 4 日かかったか(仕組み)

1. **1 回ごとのエラーメールは出ていたが、動いた人がいなかった。** 10/15 15:33 の 2 回で運営宛て(`MAIL_ALERT_TO`)に
   送られているはず。届いたか・読まれたかは外から確かめられない
2. **点検係が「再発なし」を「解消」と読んだ。** 描画で必ず落ちるエラーは「開けば 100% 落ちる」ので、
   回数が少ないのは「開いた人が少ない」だけ。10/16 の 🟡 判定(再発待ち)がそもそも甘かった
3. **運営コンソールは運営者しか開かない。** 店舗の画面と違って利用が少なく、落ちていても申告が遅れる
4. **CI(lint・型・1,300 件超のテスト・ビルド)が全部通った。** 描画しないテストは、この落ち方を捕まえられない

## なぜ直した後にメールが来たか(昼の点検の仕様)

`src/features/platform/noon-check.ts` は `error_alerts` の `last_sent_at` が直近 24 時間の行を集めて、
`occurrences` を合計し、上位 5 件を出す。確認した事実は 3 つ。

- **「修正済みか」を見ていない。** 行には「どの版で起きたか」が無い(`tenant_error_summaries` には `last_release` が
  あるが、`error_alerts` には無い)。最終発生時刻も本文に出ないので、読む人がデプロイ時刻と見比べられない
- **`occurrences` は「前回のメールを送ってからの回数」。** `error-alert.ts` はメールを送るたびに 0 に戻し、
  以後 1 時間は +1 する。だから 7 回・6 回は累計ではなく、「0 回」の行(`/dashboard/<店舗>/home` の
  React error #419)は「メールを 1 通送った後、再発していない」の意味。本文の「計 13 回」は実数より少ない
- **React error #419 は別件。** サーバーで Suspense の描画が終えられず、画面側で描き直した合図。
  Vercel のサーバーログに対応するエラーは無く、単発。原因は未特定だが、店舗一覧の件とは無関係
