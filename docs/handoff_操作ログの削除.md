## 経緯

- 要望: 管理画面の操作ログで「詳細」を開いたとき、その記録を削除できるようにする
- 2026-10-20 に仕様を決定(削除はオーナーのみ・論理削除・削除したことを記録)

- 設計の意図: 操作ログは不正や会計トラブルの証跡。誰でも消せる形にはしない

## 依頼文(ここから下をコピーして貼る)

```
管理画面の「操作ログ」で、1件の「詳細」を開いたときに、
その記録を削除できるようにしてください。

■仕様(決定済み)
1. 削除できる役割はオーナーのみ
   - スタッフ・キャストの権限では、ボタンを出さない
   - サーバー側でも役割を確かめ、オーナー以外の要求は拒否する(画面で隠すだけにしない)
2. 論理削除
   - 操作ログのテーブルに deleted_at・deleted_by の列を足す。行は消さない
   - 一覧と詳細は deleted_at が空の行だけを出す
3. 削除したことを記録
   - 「操作ログを削除」を新しい操作ログとして残す
   - 削除した記録の id・種類・日時を添える
   - この記録は削除できない
4. 画面
   - 詳細の下に「この記録を削除」ボタン
   - 押したら確認ダイアログ「この記録を削除します。元に戻せません。」
   - 確認後に一覧へ戻る
5. migration
   - 列の追加は migration で行う
   - 本番DBへの適用が先、コードはあと(POSの CLAUDE.md 6・8 に従う)

■進め方
- まず操作ログの画面・テーブル・権限の仕組みを読んで、ファイル名を確かめる
- 画面・サーバー処理・migration・テストまで実装する
- lint・型チェック・テストを通してから push し、PR を作る
- PR の説明に、migration を先に当てる手順を書く

■守ること
- 物理削除はしない
- オーナー以外が削除できる経路を残さない
- 個人情報・給与・ログイン情報は扱わない
```

## 完了の確認(新しいセッションの側で)

- [ ] オーナーでログインしたとき、詳細に削除ボタンが出る
- [ ] スタッフでログインしたとき、ボタンが出ない。直接 API を叩いても拒否される
- [ ] 削除した記録が一覧・詳細から消え、DB には行が残る
- [ ] 「操作ログを削除」の記録が新しく増え、その記録は削除できない
- [ ] migration が本番に先に当たっている
