# 引き継ぎ書: 流入経路の人数を、オーナー画面だけで変更できるようにする

作成日は2026-10-21です。
作成元は、`good` リポジトリのセッション `claude/blissful-mccarthy-j9cgi2` です。

作業先は `pokkiriofficial/nightwork-pos`(POS 本体)です。
新しいセッションを始めるときに、対象リポジトリとして選んでください。

## 結論

今回の依頼は、POS 本体の変更です。
`good`(アンケートキット)側の変更は、不要の見込みです。

方針は A案 で決まっています。
会計で記録された、流入経路ごとの来店人数の集計値を、
オーナーだけが手で補正できるようにします。

前のセッションでは、nightwork-pos を取り込めませんでした。
権限の判定に拒否されたためです。

そのため、POS のコードは1行も読んでいません。
この書類の「わかっていること」は、`good` にあった資料の内容です。
コードを読んで確かめた事実ではありません。

## 依頼の内容

依頼の原文は、次のとおりです。

> ポッキリ.Nightの流入経路の人数をオーナー画面のみで変更できるようにして

「人数」の意味には、2つの案がありました。

A案は、集計値をオーナーだけが手で補正できる案です。
B案は、人数は自動集計のままにして、
オーナー画面でだけ変更を許す案でした。
B案は採用していません。

## わかっていること(`good` の資料より)

流入経路は、お客様がどこから来たかを記録する項目です。
初期の選択肢は、新規・リピーター・紹介・SNS・ビラ・看板の6つです。
店舗があとから追加できます。

会計のときに選んで記録します。
金額の計算には影響しません。
これらは `spec/items.yaml` の `referral_tags` と、
`docs/pos_handoff.md` の S9 に書かれています。

設定画面の目次には、「流入経路(タグ名の追加)」があります。
ただし、これは試作の見本画面です。
本物の画面ではありません(`templates/catalog/preview.html:204`)。

権限の役割は、`owner`・`manager`・`staff` の3つです。
店長の発行は、初期状態でオンです。
これは、過去の事故記録に載っていたコードから読み取りました。

認証まわりのファイルは、次の3つが挙がっています。
`src/features/auth/session.ts` には、デモ用オーナー設定があります(82〜83行目)。
`src/features/floor/actor.ts` は、フロアの PIN です。
`src/features/auth/credentials/role-login.ts` は、ログインの処理です。

## まだわかっていないこと

新しいセッションの最初に、次の5つを調べてください。
どれも読み取りだけで済みます。

1つめは、流入経路の保存場所です。
どのテーブルの、どの列に入っているのかを調べます。
会計1件ごとなのか、人数つきなのかも確かめます。
補正値を足す場所が、これで決まります。

2つめは、人数の集計を出している画面です。
ダッシュボード、帳票、運営コンソール、CSV などが考えられます。
補正値を全部の表示に反映しないと、画面ごとに数字が食い違います。

3つめは、オーナー画面の場所と、権限チェックの方法です。
変更を許す入口は、ここになります。

4つめは、店長やスタッフが、今の画面や API で
人数を変えられてしまう経路がないかです。
「オーナーのみ」を破る穴を、先に洗い出します。

5つめは、流入経路の集計が、
給与・バック・売上の計算に使われていないかです。
使われていれば、補正の影響範囲が広がります。

## 重要な論点

### 1. 「オーナーのみ」は、サーバー側で守る

画面でボタンを隠すだけでは、足りません。
API や Server Action の入口で `owner` かどうかを確認し、
`manager` と `staff` は拒否します。

テストでも、店長が拒否されることを固定してください。
依頼の核心は、ここにあります。

### 2. 補正は、元の記録を変えずに別に持つ(推奨)

元の会計記録は、書き換えません。
補正値を別に持ち、「実績・補正・合計」を出せる形にします。

理由は2つあります。
あとで実績との食い違いを説明できることと、元に戻せることです。

ただし、保存の形がまだ未確認です。
前の項目の調査結果を見て、最終的に決めてください。

### 3. 変更の記録を残す(推奨)

誰が、いつ、どの経路を、何人から何人に変えたかを残します。
オーナーが1人の店でも、後日の説明に必要です。

### 4. デモ用オーナー設定を、最優先で確認する

本番の環境変数に、次の2つが設定されていないか確かめます。
`PUBLIC_DEMO_TENANT_ID` と `PUBLIC_DEMO_OWNER_USER_ID` です。

設定されていると、未ログインの誰でも、
そのテナントのオーナーとして書き込めます。
その場合は、「オーナーのみ」が成り立ちません。

確認するのは、Vercel の環境変数の「名前」だけです。
値は見ません。出力もしません。
設定されていたら、実装より先にユーザーへ報告してください。

なお、本番に設定されているかは、まだ確認できていません。

### 5. 集計を出す全部の画面に反映する

補正が一部の画面にしか効かないと、
画面ごとに人数が違って見えます。
反映する画面の一覧を作り、ユーザーと合意してから実装してください。

## 守ること

最初に、nightwork-pos の `AGENTS.md` を読んでください。
POS 側の決めごとが書かれています。
事故記録には、ルール19(描画のテスト)も出てきます。

画面を描画するテストを足してください。
オーナーで開いた場合と、店長で開いた場合の両方です。

2026-10-14から18まで、運営コンソールが4日間開けませんでした。
宣言より前の行で変数を読んでいたことが原因です。
CI は全部通っていましたが、描画するテストがありませんでした。
関数の中から、後ろで宣言する `const` を読まないでください。

migration を足す場合は、`_journal.json` の `idx` と `when` を、
必ず増える順に並べます。
逆順だと、本番に永久に当たりません。

migration は、他の作業とぶつかりやすいです。
着手の前に、open の PR を見てください。
同じ領域の PR や、未マージの migration がないかを確かめます。
2026-10-15には、同じ修正の PR が2本並びました。

変更の前に、`git status --short` が空であることを確認してください。
本番作業の作業ツリーと、ぶつけないためです。

画面の文言は、POS 側の流儀を優先してください。
`good` の決めごとでは、用語は「キャスト」「スタッフ」「卓」「伝票」「バック」です。
1行は20〜35文字、読点は1文に1〜2個です。

個人情報・給与・ログイン情報は、新たに扱いません。
人数の補正は、これに当たらない想定です。

PR は、ユーザーが頼むまで作りません。
作業ブランチに push するところまでです。

## 進め方

1. nightwork-pos の最新の main を取得し、`AGENTS.md` と、
   「まだわかっていないこと」の5つを調べます。

   あれば、実装より先に報告します。
3. 調査結果を10行以内でユーザーに示します。
   補正の持ち方と、反映する画面の一覧について、合意を取ります。
4. 実装します。

   オーナーだけが使える入口、変更の記録、集計表示への反映です。
5. テストを足します。
   オーナーは変更できること、店長とスタッフは拒否されること、
   描画テスト、集計に補正が反映されることです。
6. lint・型・テスト・ビルドを通し、結果をそのまま報告します。
   失敗があれば、失敗と書いてください。
7. 作業ブランチに push します。PR は指示を待ちます。

## 完了の条件

オーナーだけが、人数を変更できることです。
店長とスタッフが API を直接呼んで、拒否されるテストで確かめます。

変更した人数が、集計を出すすべての画面に反映されることです。
「まだわかっていないこと」の2つめの一覧と、突き合わせます。

変更の記録が残ることです。
記録テーブルの行で確認します。

会計の金額に影響しないことです。
既存の会計テストが、全部通ることで確かめます。
